# Local performance diagnostics

Settings → Application → **Record local performance diagnostics** is off by default. Enabling it starts a resource sample once a minute and coalesced samples around window closure. Disabling it stops sampling immediately. This setting does not upload data or read screenshot pixels, OCR text, window titles or private file paths.

`resources.log` and `resources.previous.log` live beside the application's settings. Each is capped at 1 MiB; a bounded queue drops excess samples rather than blocking capture. This budget retains a representative full day of minute samples, with additional window samples shortening retention. Basic `diagnostics.log` records include build/session identity and session start/stop. The resource log contains UTC time, session, full build version/commit, resident/private/managed memory, OS peak resident memory, sampled private/handle peaks, CPU interval and cumulative counters, GDI/USER handles, threads, GC collection/heap counters and dispatcher queue delay. CPU percent is relative to one logical core. The first sample has no interval CPU value.

Only one resource read/dispatcher callback may be pending. If the dispatcher is busy, requests coalesce and its eventual queue delay is recorded. The five-second window recovery sample is also coalesced; it does not force garbage collection. Sleep/resume and system load can affect dispatcher delay. Sampled peaks can miss short spikes and are distinct from the OS peak working set.

For an all-day review, enable the option, restart so startup is represented, use normal capture/editor/history/pin/OCR workflows and leave the app idle between them. Preserve the two local resource logs, basic log and installed build provenance before they rotate. Compare cumulative CPU differences and memory/handle recovery after windows close. A rising working set alone is not a leak verdict. This implementation does not close the current all-day or prolonged stress acceptance gates.
